Benchmarks

Measured. Reproducible. On modest hardware.

Overview

A mid-size city. A laptop. Under a millisecond.

10,000 properties · 6 room types × 3 rate plans · 30 days of availability and rates. Filtered to ~333 winners per query. Measured end-to-end, through the HTTP API.

No warmup. No cherry-picked runs. The API server and the benchmark share the same runtime, so the numbers below are conservative.

What's in the query

Filtering

10,000 properties reduced to ~333 candidates by district, with room-type and bed filters applied. Microseconds, not milliseconds.

Pricing

Each surviving property is priced for the query: rate, child supplements, charges, promotions. About 6,000 candidate rate cells are evaluated per search.

Allocation

For multi-room queries, the engine picks the cheapest combination that covers the party. The 2-room case shows the extra cost: an additional ~1.2 ms at p50.

Serialization

HTTP and JSON add ~200–350 µs to the internal search time. On loopback. In production, network distance dominates, not the engine.

Caveats

These are honest numbers from modest hardware.

  • · Laptop-class CPU. Production servers have more cores and wider memory bandwidth.
  • · Loopback network. Real clients add network latency, not engine cost.
  • · Fixture is synthetic. Real property mixes vary. Filter tightness changes the number of candidates and therefore the time.

The engine prices thousands of candidate rate cells in under a millisecond, end to end, on a laptop — including filters, pricing, and HTTP. The cost is dominated by how many candidates survive the filter, not how many properties exist.
