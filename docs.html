Overview

Read this first. It's the twenty-minute version of every other page.

The pain

Search is not a lookup. For a booking engine, "find me a room" means three questions asked at once:

  • Which properties match? Location, dates, rating, facilities, capacity, policies.
  • What does each one cost? Rate, child pricing, charges, taxes, promotions — computed per query, not stored.
  • What is the cheapest valid combination? Especially when the party needs more than one room, or mixes adults and children.

Most teams solve this with two systems bolted together. A search engine (Elasticsearch, Redis) answers the first question. A rules engine answers the second. Keeping them in sync is the third, permanent problem.

The result is fragile. Prices drift. Caches miss. Latency spikes. The team spends its time on infrastructure, not on the product.

The solution

Veyoz does all three in one engine.

  • Filter. Bitmap indices reduce tens of thousands of properties to a few hundred candidates in microseconds.
  • Price. Every surviving property is priced for the specific query — rate, child supplements, charges, promotions, restrictions — with no pre-computed price.
  • Rank. For multi-room queries, the cheapest combination that covers the party is chosen deterministically.

The state is held in memory, replicated through Raft, and served by followers. There is no search index to keep in sync and no cache to invalidate. When a rate changes, the state changes; the next search sees it.

How you integrate

1

Seed the state.

Export your properties, rooms, rates, calendars, charges, and promotions to CSV. Run veyoz snapshot to build a snapshot, and boot each node from it. Millions of records load in seconds.

2

Send deltas.

After bootstrap, everything is a REST call: new properties, rate changes, availability updates, calendar edits. The leader replicates them; every follower applies them in the same order.

3

Search.

One POST /api/search call returns priced, ranked results. Followers serve reads; add a follower to add read capacity.

Your database stays the source of truth for cold data and far-future dates. Veyoz holds only the hot booking window in memory.

What Veyoz is not

  • Not a booking system. Reservations, payments, and confirmations stay where they are.
  • Not a channel manager. You send us normalized data; we don't fetch from aggregators.
  • Not a ranking engine. We return the cheapest valid result. Ranking is your product decision.
  • Not a general-purpose database. It does one thing: search with pricing.

Models

These are the wire models exchanged with the API. All fields are JSON. Money is always an integer in the smallest currency unit (e.g., EUR cents). Dates are ISO 8601 (YYYY-MM-DD). Country codes are ISO 3166-1 alpha-2, uppercase.

Deployment

Run a node in the Veyoz cluster.

CLI Usage

veyoz run \
  --node-id <NODE_ID> \
  --shard-id <SHARD_ID> \
  --zone-id <ZONE_ID> \
  --cert-path <CERT.pem> \
  --key-path <KEY.pem> \
  --ca-cert-path <CA.pem> \
  --resolver-addr <RESOLVER_URL> \
  [--config <CONFIG.yaml>] \
  [--initial-voters <ID1,ID2,...>] \
  [--api-listen-addr <ADDR>] \
  [--quic-listen-addr <ADDR>] \
  [--data-dir <PATH>]

Required Arguments

  • --node-id — Unique identifier for this node.
  • --shard-id — Unique identifier for the shard.
  • --zone-id — Identifier for the zone this node belongs to.
  • --cert-path — Path to the TLS certificate file.
  • --key-path — Path to the TLS private key file.
  • --ca-cert-path — Path to the CA certificate file.
  • --resolver-addr — Resolver service base URL.

Resolver Service

--resolver-addr points to an external HTTP service that you implement. Veyoz does not ship one.

When a node needs to reach another node by id, it calls: 

GET {resolver_addr}/{node_id}

→ 200 OK
  <hostname>

The response body is the hostname (or address) of the node as a plain string.

This decouples Veyoz from your infrastructure. DNS, IPs, and topology can change however you like — the resolver is the only place that knows. Veyoz never needs to be reconfigured when your network changes.

Optional Arguments

  • --config — Path to the YAML configuration file.
  • --initial-voters — Comma-separated list of node IDs for initial voting members.
  • --api-listen-addr — API listen address (overrides config).
  • --quic-listen-addr — QUIC listen address (overrides config).
  • --data-dir — Data directory path (overrides config).

Configuration File

Values in the YAML config can be overridden by CLI flags. Identity, paths, and external service settings (marked with CLI only) are not read from the YAML file.

Cluster

  • quic_listen_addr — QUIC listen address. Default: 0.0.0.0.
  • quic_port — QUIC listen port. Default: 17777.
  • raft_tick_ms — Raft tick interval in milliseconds. Default: 30.
  • raft_election_tick — Raft election tick count. Default: 60.
  • raft_heartbeat_tick — Raft heartbeat tick count. Default: 15.

Server

  • api_listen_addr — API listen address. Default: 0.0.0.0.
  • api_port — API listen port. Default: 8080.
  • snapshot_interval_sec — Interval between snapshots in seconds. Default: 60.
  • snapshot_trigger_count — Number of log entries before triggering a snapshot. Default: 10_000.
  • wal_flush_threshold — WAL flush threshold in entries. Default: 2000.
  • search_queue_timeout_ms — Search queue timeout in milliseconds. Default: 10.

Cluster Membership

--initial-voters is the seed list of voting members. If a node's ID is not present in the seed list, it joins the cluster as a learner instead of a voter.

TLS Certificates

For node-to-node communication, only the certificate chain and expiration dates are validated. Hostname verification is not performed.

API

HTTP API for reading and writing Veyoz data. All data routes are under /api. Bodies and responses are JSON. Model shapes are defined in Models.

Availability & Middleware

  • Node availability. Every /api route is gated. A node with no quorum returns 503 with { "error": "node unavailable: cluster lost quorum" }.
  • Compression. gzip, brotli, and zstd are negotiated.
  • CORS. Any origin, any method, any header.

Bulk Import

Build a seed snapshot offline from CSV files. Provide the CSVs, run veyoz snapshot, and load the result on each bootstrapping node.

Flow

your DB  →  export CSVs  →  veyoz snapshot  →  snapshot dir  →  copy to node(s)  →  veyoz boots from it

Veyoz loads millions of records in seconds from the snapshot. After that, you only send deltas through the API.

CLI Usage

veyoz snapshot \
  --shard-id <SHARD_ID> \
  --input-path <CSV_DIR> \
  --output-path <SNAPSHOT_DIR>
  • --shard-id — Unique identifier for the shard this snapshot belongs to.
  • --input-path — Directory containing the CSV files.
  • --output-path — Directory where the snapshot will be written.

Output

The builder writes the following into the output directory, plus a .zip archive next to it:

  • manifest.json — Snapshot metadata.
  • props.bin — Filter bitmaps.
  • mapper.bin — Code ↔ slot tables.
  • review_scores.bin — Per-property review scores.
  • min_ages.bin — Per-property minimum child ages.
  • meta.bin — Per-property metadata.
  • bucket_*.bin — Property pages, sharded across buckets.

Format Rules

  • Encoding — UTF-8. Non-UTF-8 bytes are rejected.
  • Separator — Comma (,). No quoting, no escaping, no commas inside values.
  • Header — Every file must have a header row. It is skipped and not validated.
  • Multi-value fields — Pipe-separated (1|2|3).
  • Empty fields — Mean "not set" for optional values.
  • Money — Integers in the smallest currency unit (e.g., EUR cents). No decimals, no floats.
  • Dates — ISO 8601 (YYYY-MM-DD).
  • Country codes — ISO 3166-1 alpha-2, uppercase (US, TR, DE). Lowercase is accepted and normalized to uppercase.
  • IDs — Integers.

Files

Place all CSVs in one input directory. File names are fixed.

  • properties.csv — Required. One row per property.
  • room_types.csv — Optional. One row per room type.
  • room_rates.csv — Optional. One row per rate plan.
  • availability.csv — Optional. One row per (room type, date).
  • calendar.csv — Optional. One row per (rate plan, date).
  • charges.csv — Optional. One row per charge.
  • promotions.csv — Optional. One row per promotion.

If an optional file is absent or empty (header only), that entity is treated as "none" for all properties.

RLO offset rules

  • persons — the occupancy this offset applies to. Must differ from rlo_leading_occupancy.
  • type = Percentage — value is a whole percent (e.g., 25 = +25%, -15 = −15%). Minimum -100.
  • type = Absolute — value is in the same unit as prices (smallest currency unit).
  • round = true — round the final adjusted price down.

Child pricing rules

  • bucket — index into the property's child_buckets (0-based).
  • index — 0-based position within the bucket, must be < child_max_per_bucket.
  • amount — fixed monetary amount, same unit as prices. Percentages are not supported; resolve them upstream.
  • per_stay — true = charge once per stay. false = charge per night.
  • Missing cells default to free (0).

Period modes

PerNight, PerStay, PerPersonPerNight, PerPersonPerStay, Percentage, Incalculable, PerDay, PerPersonPerDay, Variable.

  • PerDay and PerPersonPerDay charge for nights + 1 days (both stay endpoints inclusive).
  • Variable is not computed by the engine. Charges with this mode are skipped.

Amount units by mode

  • PerNight, PerStay, PerPersonPerNight, PerPersonPerStay, PerDay, PerPersonPerDay — smallest currency unit.
  • Percentage — whole percent (e.g., 10 = 10%).
  • Incalculable, Variable — ignored.

Excluded

  • false — Charge is included in the displayed price.
  • true — Charge is paid at the property. Returned in a separate excluded_taxes field in search and matrix responses, and not added to total.

Percentage base (only for mode = Percentage)

+-separated combination of NetRoomPrice, PropertyCharges, LocalityCharges. Must include NetRoomPrice. A charge cannot base itself on its own category (e.g., a CleaningFee cannot include PropertyCharges).

child_multipliers

Applies to the entire charge. If the charge has multiple periods, they all receive the same bands. Applies only to PerPersonPerStay and PerPersonPerNight modes; TransferFee is the sole exception among PropertyCharges-category types.

Specificity

When a property has multiple charges of the same charge_type, only the most specific match applies. Priority order:

  1. guest_origin and travel_purpose both specific (e.g., International + Leisure).
  2. One specific, one Any.
  3. Both Any.

Room-level charges take priority over property-level charges of the same type.

Rules and Constraints

Required consistency

  • Every property_id in child files must exist in properties.csv.
  • Every room_type_id in room_rates.csv and availability.csv must exist in room_types.csv.
  • Every rate_plan_id in calendar.csv must exist in room_rates.csv.
  • Every calendar row's pricing_type must match the rate's declared pricing_type.
  • Every (rate_plan_id, date) pair in calendar.csv must be unique.
  • Every (room_type_id, date) pair in availability.csv must be unique.
  • room_type_id in charges.csv (when level = Room) must exist in room_types.csv.
  • charge_id must be unique within a property.
  • promotion_id must be unique within a property.

Limits

  • 64 distinct property filter codes across the dataset.
  • 64 distinct room feature codes.
  • 32 distinct bed types.
  • 64 distinct rate value-add codes.
  • Child age buckets: up to 4 per property.
  • LOS pricing: max nights defined by rate.

What is not checked

  • That your data is semantically correct (e.g., that prices are reasonable).
  • That stay_date_start <= stay_date_end in promotions.
  • That room max_adults + max_children >= max_occupancy.

Veyoz trusts the CSV. Invalid data produces invalid search results.

Error Messages

Snapshot build errors reference the file name and the failing row. Common causes:

  • "invalid utf8" — a CSV contains non-UTF-8 bytes.
  • "bad u32: ..." — a numeric field is not parseable.
  • "room_type references unknown property N" — an orphan row.
  • "bad pricing_type: ..." — misspelled pricing type.
  • "bad offset_type: ..." — misspelled RLO offset type.
  • "weekday out of range: N" — a weekday value outside 1–7.
  • "duplicate charge id: N" — a charge id appears twice for the same property.
  • "duplicate promotion id: N" — a promotion id appears twice for the same property.

Fix the row, rebuild.
